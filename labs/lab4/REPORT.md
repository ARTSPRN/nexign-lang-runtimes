### Задача A. Теория Большого взрыва

Замеры делал на Linux x86-64, GCC 16.2.0. Размер кэш-линии L1d - 64 байта (`getconf LEVEL1_DCACHE_LINESIZE`)

Команды сборки из корня репозитория:

```bash
cd labs/lab4
build_dir=$(mktemp -d)
g++ -std=c++20 -Wall -Wextra solution/mixed.cpp -o "$build_dir/mixed"
g++ -std=c++20 -O3 -march=native -Wall -Wextra \
    -fopt-info-vec-optimized="$build_dir/vectorization.txt" \
    solution/particles.cpp -o "$build_dir/particles"
g++ -std=c++20 -O3 -Wall -Wextra -g -pthread solution/bench.cpp -o "$build_dir/bench"
cd "$build_dir"
```

#### Этап 1. Упаковка структур и выравнивание полей

> Прогноз: обычная структура займёт 32 байта из-за выравнивания, упакованная - 16 байт. GCC предупредит, что адрес `d` может быть невыровненным

```bash
for i in {1..5}; do ./mixed; done
```

При сборке GCC выдал:

```text
solution/mixed.cpp:22:29: warning: taking address of packed member of ‘PackedMixed’ may result in an unaligned pointer value [-Waddress-of-packed-member]
```

Пример вывода:

```text
Mixed: 32 bytes, alignment 8
PackedMixed: 16 bytes, alignment 1
Fields: 16 bytes
Offset of d: 16 / 6
Address of packed d: 0x7ffc4deb2196
```

> Во всех пяти прогонах размеры и смещения совпали с прогнозом. Размер упакованной структуры равен сумме размеров полей: `1 + 4 + 1 + 8 + 2 = 16` байт. В обычной структуре есть промежутки между полями и в конце, чтобы поля оставались выровненными и в массиве структур
>
> Адрес из примера не кратен 8. Обычный `double*` предполагает, что объект выровнен, поэтому разыменовывать такой указатель нельзя. Некоторые процессоры могут вызвать исключение при невыровненном чтении. На x86 многие инструкции допускают такой доступ, но чтение может стоить дороже, если поле пересекает границу кэш-линии. В эксперименте я только вывел адрес

#### Этап 2. AoS и SoA

> Прогноз: SoA будет быстрее. Физическому шагу цвет не нужен, а с отдельными массивами он не занимает место в загружаемых кэш-линиях. Координаты и скорости идут подряд, поэтому их проще обрабатывать с помощью SIMD

```bash
for i in {1..5}; do
    if (( i % 2 )); then modes=(aos soa); else modes=(soa aos); fi
    for mode in "${modes[@]}"; do taskset -c 0 ./particles "$mode"; done
done
```

В каждом прогоне по 10 млн частиц. Засекал только шаг обновления трех координат. Инициализация и подсчёт суммы координат выполнялись отдельно. Сумма в обоих вариантах во всех прогонах получилась `15434631360`

| Вариант | Прогоны, мс | Медиана, мс | Минимум, мс |
|---|---|---:|---:|
| AoS | 104,849 / 111,579 / 75,093 / 141,876 / 68,734 | 104,849 | 68,734 |
| SoA | 69,879 / 47,729 / 44,605 / 132,971 / 76,945 | 69,879 | 44,605 |

> По медиане SoA быстрее в `104,849 / 69,879 ≈ 1,50` раза, что совпало с прогнозом. В пятом прогоне AoS оказался быстрее. Из-за разброса отдельных замеров сравнивал по медиане. На длительность отдельного прогона могли влиять частота CPU и нагрузка от других процессов
>
> При обходе AoS в среднем приходится `64 × 24 / 28 ≈ 54,9` полезного байта на линию. Из 28 байт частицы используются 24 байта координат и скоростей, ещё 4 байта занимает цвет. В отдельных линиях доля может отличаться, потому что частицы пересекают их границы. В SoA полная линия любого из шести используемых массивов даёт 64 полезных байта, то есть 16 значений `float`. Массив цветов в шаге вообще не читается. Оба варианта хранят те же поля и занимают 280 МБ под сами данные, но шаг проходит по 280 МБ в AoS и по 240 МБ в SoA
>
> В SoA соседние значения одной координаты лежат подряд и загружаются одним SIMD-вектором. В AoS одинаковые поля отстоят друг от друга на 28 байт, поэтому обрабатывать сразу одну координату нескольких частиц сложнее. По отчёту GCC цикл SoA использовал 32-байтовые векторы, а цикл AoS - 8-байтовые. В SoA я объявил указатели `__restrict__`, так как все шесть массивов отдельные. Это позволяет GCC векторизовать цикл без проверок на пересечение массивов
>
> AoS может оказаться лучше при обращении к отдельным частицам по случайным индексам, когда нужны все их поля. Например, для вывода выбранной частицы со всеми её параметрами координаты, скорости и цвет уже лежат рядом. В SoA за ними надо идти в семь массивов

### Задача B. Вне конкуренции

#### Этап 1. Воспроизведение false sharing

> Прогноз: счётчики в двух линиях будут работать быстрее. Если оба счётчика в одной линии, каждому ядру придётся получать её для записи снова после изменений на другом ядре

```bash
lscpu -p=CPU,CORE,SOCKET
for i in {1..5}; do
    if (( i % 2 )); then modes=(adjacent padded); else modes=(padded adjacent); fi
    for mode in "${modes[@]}"; do taskset -c 0,1 ./bench "$mode"; done
done
```

| Вариант | Прогоны, мс | Медиана, мс | Минимум, мс |
|---|---|---:|---:|
| A, рядом | 3386,537 / 3419,680 / 3282,252 / 4281,820 / 3985,311 | 3419,680 | 3282,252 |
| B, раздельно | 1343,390 / 1128,831 / 1287,462 / 1310,251 / 1426,978 | 1310,251 | 1128,831 |

> Раздельные счётчики оказались быстрее в `3419,680 / 1310,251 ≈ 2,61` раза по медиане. В первом прогоне A адреса были `0x7fffeea75600` и `0x7fffeea75608`, оба в одной линии. В первом прогоне B они были `0x7ffd98c50dc0` и `0x7ffd98c50e00`, разница 64 байта
>
> `lscpu` показал строки `0,0,0` и `1,1,0`: CPU 0 и CPU 1 находятся на разных физических ядрах одного сокета. `taskset` оставляет эти два CPU в маске программы. Каждый поток дополнительно закрепляется за одним CPU через `sched_setaffinity`. Во всех запусках проверки через `sched_getcpu()` до и после цикла дали `0 -> 0, 1 -> 1`. В конце оба счётчика были равны `100000000`
>
> Ядро получает право записи на всю кэш-линию. Когда первый поток меняет свой счётчик, копия линии у второго ядра становится недействительной. Второму ядру тоже нужна эта линия для записи, поэтому ядра постоянно передают друг другу право записи. `memory_order_relaxed` ослабляет требования к порядку атомарных операций, но запись всё равно требует владения линией
>
> Если добавить потоки на разных ядрах и разместить их счётчики в той же линии, за право записи будут бороться больше ядер. Линия будет чаще переходить между ними. Если счётчиков больше восьми, они займут несколько линий и конкуренция будет происходить между ядрами, пишущими в одну линию

#### Этап 2. Поиск false sharing с помощью `perf c2c`

> Прогноз: на этой машине один сокет, поэтому ожидаю увидеть локальные HITM на линии соседних счётчиков. Смещения счётчиков в ней должны быть `0x00` и `0x08`

```bash
perf c2c record -o perf.data -- taskset -c 0,1 ./bench adjacent
perf c2c report -i perf.data --stdio
```

На машине изначально не было `perf`. Для пробы запустил `perf` 7.3.5 из распакованного Debian-пакета `linux-perf` во временной папке. Ядро запретило запись событий. Фрагмент вывода:

```text
Failure to open event 'cpu/mem-loads,ldlat=30/Pu' on PMU 'cpu' which will be removed.
Access to performance monitoring and observability operations is limited.
perf_event_paranoid setting is 3:
```

То же произошло с событием `cpu/mem-stores/Pu`. Запись закончилась сообщением `Failure to open any events for recording.`, при чтении отчёта получилось `zero-sized data (perf.data), nothing to do!`

> Сам `bench` показывает, что в варианте A первым счётчиком (`counters[0]` по смещению `0x00`) занимается CPU 0, а вторым (`counters[1]` по смещению `0x08`) - CPU 1. Это видно по адресам и привязке потоков. Конкретную строку с наибольшей конкуренцией в `Shared Data Cache Line Table` определить не удалось, так как сэмплов нет. Разница во времени согласуется с false sharing. Подтверждение через HITM требует повторить запись на машине с доступом к событиям PMU и сопоставить адрес линии из запуска `adjacent` со строкой таблицы и её детализацией `Cacheline`. На одном сокете стоит смотреть прежде всего на `Lcl HITM`, а для обмена между сокетами - на `Rmt HITM`

#### Вывод

Для одинаковых действий над большим числом частиц подходят отдельные массивы часто используемых полей. Счётчики, в которые постоянно пишут разные ядра, лучше разместить в отдельных кэш-линиях. Упаковка экономит память, но адреса отдельных полей могут оказаться невыровненными
